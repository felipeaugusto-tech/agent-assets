Project Slipstream · GenDD Practice · Plugin architecture · v2

One plugin, thirty-four commands

Your sketch, made buildable — and simplified. The whole GenDD workflow ships as the single gendd plugin that already exists, grown from one skill to thirty-four, assembled from the agent-assets corpus by a small build step. This replaces the six-plugin version of this plan; section 02 explains why, including where my earlier recommendation was wrong.

Three of the thirty-four are on disk. Phase 0 is complete and verified.

enhance-requirements — shipping since v0.1.0. run-brownfield-analysis — authored, untested against a real repository. adr-writer — vendored from its .skill package, which proves the import mechanic for the other twelve. The sync script covers both source types.

The live status, the exact commands and the test plan are in claude-plugin-poc/4-skill-packaging.md; this page is the reasoning behind them. Both are on disk in the repo, so a Claude Code session can read them directly.

Rule 1

Nothing existing is edited

Not the corpus, not marketplace.json, not plugin.json. Only additions under claude-plugin-poc/.

Rule 2

Every skill keeps its name

adr-writer, not write-adr. The existing .skill name wins, then the corpus filename. New names only where none exists.

Rule 3

One namespace, no migration

Everything is /gendd:<name>. /gendd:enhance-requirements keeps working exactly as it does today.

Rule 4

One script, no framework

Corpus content is copied into references/ by ~18 lines of shell whose copy lines double as the map. --check proves the copies still match.

01 · THE FINDING THAT SHAPES EVERYTHING

A plugin cannot read a file outside its own root

There is no documented way for a skill to reach ../../gendd-analysis/. So the corpus content each skill needs has to be physically inside the plugin — which means the plugin is built, not hand-assembled. This is true whether there is one plugin or six.

The variables a plugin gets are ${CLAUDE_PLUGIN_ROOT}, ${CLAUDE_PLUGIN_DATA} and ${CLAUDE_PROJECT_DIR}; none reaches a sibling directory. Traversal out of the plugin root is undocumented, symlink survival is undocumented, and the git-subdir source type — the one built for monorepos — sparse-clones only the plugin's own subdirectory, so on that path the rest of the repo provably isn't there.

Your POC reached this conclusion the hard way and solved it by copying three files byte-for-byte. That was right, and it produced the exact problem worth designing out: enhance-requirements now exists in four places and the copies won't follow an edit to the source. Thirty-four skills means roughly seventy copied files with the same failure mode.

So keep the copying and make it a script with a check. The corpus stays the single source of truth and is never touched; the plugin's skills/ and references/ become generated output; and one command proves the output still matches the corpus. Byte-fidelity, no drift, nothing maintained twice.

02 · WHY ONE PLUGIN, NOT SIX

The main argument for splitting doesn't survive scrutiny

I recommended per-occupation plugins earlier. The benefit I claimed was per-group enablement — and that benefit largely isn't available, which changes the answer.

The correction

Managed settings can't scope by group

Server-managed settings apply org-wide and uniformly — per-group configuration is not supported. So you could never have enabled gendd-engineering for engineers and gendd-qa for QA through the channel you're actually using. Splitting would only have bought opt-in through project-level settings, which is a far smaller benefit than I implied.

Your own corpus says so

Most capabilities are multi-role already

playbooks/on-demand/_index.md lists target roles per playbook, and nearly every one crosses occupations: create-context-pack is Architect + Tech Lead + Backend + Frontend + Fullstack; enhance-requirements is PO + BA + QA; generate-unit-tests is three dev roles + QA Automation. Per-occupation plugins would force an arbitrary home for each, and a frontend dev needing validate-acceptance-criteria would have to install the QA plugin.

The practical win

Zero edits, zero retraining

The marketplace entry already points at ./claude-plugin-poc, so marketplace.json needs no change at all and enabledPlugins stays as it is. And because namespacing is by plugin name, keeping one plugin means /gendd:enhance-requirements stays exactly what people already type. The six-plugin plan required renaming the one command currently in the field.

What you give up · the real one

Independent release cadence

One plugin, one version. A QA skill and a PO skill ship together, so a bad QA release bumps the version everyone has. This is the genuine argument for splitting later, and the signal to watch for: the first time you want to hold one area back while shipping another.

What you give up · measurable

~2,000 tokens of standing cost

Every skill's name and description loads at session start. At Anthropic's projected ~59 tokens for a manual-only skill, thirty-four skills is roughly 2,000 tokens in every session — for everyone, including a PO who will never call generate-unit-tests. Measure it with scripts/benchmark-plugin.sh before treating it as a problem. That is what the harness is for, and it is the number that decides whether to split.

One carve-out

Keep the TestRail MCP separate

MCP tool schemas are always-on for anyone who has the plugin, unlike references which cost nothing until invoked. Bundling the TestRail server into the single plugin taxes every PO and architect with tool definitions they will never call. Configure it per project, or make it the one small second plugin — gendd-testrail — enabled only where QA works.

Read only · the corpus

Never written by anything

The build reads from gendd-analysis/, sdlc/, governance/, templates/ and code-and-test-templates/. An edit there is the only way methodology changes — and --check is what makes that edit propagate on purpose rather than by accident.

Written by hand · skills/

Authored in place, left alone

A SKILL.md is never derived from anything, so it doesn't belong in a build pipeline. It says what the steps are and which reference files to load; it never restates the method, because the method is in the corpus. enhance-requirements doesn't move at all.

Generated · references/ and vendored skills

The only thing the build owns

Committed anyway, because installation is a git clone with no build hook. Generated because of the finding in section 01. Treat a hand edit here the way you'd treat editing node_modules — the next build wipes it, and --check catches it first.

04 · HOW THE COPYING STAYS HONEST

Two maps, one script, one check

Deliberately not part of phase 0 — with one skill and three already-correct copies it would have produced nothing. It arrived with skill #2, and grew a second map with skill #3. Its value is drift detection. Because the corpus and the plugin live in the same repository, that needs no hashes: no lockfile, no provenance file, no separate map. The copy lines are the map and --check is the verifier.

1 · THE MAP, WHICH IS ALSO THE SCRIPT

sync_references.py

The one place that says this reference came from this corpus file. The narrow reason it can't be inferred instead: create-context-pack.md exists in both workflows/ and playbooks/on-demand/ — as do generate-ide-rules.md, generate-unit-tests.md, identify-test-gaps.md and generate-architecture-diagrams.md. Five deliberate basename collisions, because the workflow/playbook pairing is the corpus's own design. A generic "find the file with the same name and diff it" check would silently compare against the wrong source for exactly the capabilities you are most likely to package.

Written as a Python list rather than a separate YAML map: the declaration then sits next to the code that acts on it, needs no parser, and reviews as a one-line diff. Python rather than shell because the engineers are on Windows and this repo already depends on it — the TestRail MCP server, lint_c4.py and scan_pipeline.py are all Python. It runs unchanged in PowerShell, Git Bash, macOS and Linux.

# sync_references.py — the two maps and the check
REFS = [   # corpus documents → references/<skill>/
    ("enhance-requirements", "gendd-analysis/playbooks/on-demand/enhance-requirements.md"),
    ("enhance-requirements", "gendd-analysis/workflows/enhance-acceptance-criteria.md"),
    ("enhance-requirements", "gendd-analysis/templates/requirements-enhancement.md"),
    ("run-brownfield-analysis", "gendd-analysis/playbooks/onboarding/run-brownfield-analysis.md"),
    # … and the four pass agents, the guidelines, the methodology
]

VENDORED = [   # vendor/*.skill → skills/<name>/, unpacked verbatim
    "adr-writer.skill",
]
2 · THE CHECK

--check, and why it is the whole point

Same code, a temp destination, then diff -r. Because the corpus and the plugin live in the same repository, verification needs no hashes and no lockfile — it can simply rebuild and compare. One mechanism, both failure modes:

— A corpus file changed and nobody re-synced. The temp build differs from the committed copies, so the plugin is shipping stale text. This is the failure that already happened to enhance-requirements.

— Someone hand-edited a generated file. Same diff, opposite direction. Worth catching, because the next sync would silently wipe their change.

Wire it into CI beside lint-standards.sh, with claude plugin validate --strict in the same job. Deleting the destination before rebuilding is what makes a removed entry actually disappear rather than linger as an orphan.

3 · THE LOOP

Local, before anything is published

No marketplace entry needed — --plugin-dir loads a plugin straight off disk, and /reload-plugins picks up a change without restarting the session.

# nothing published, nothing installed
python claude-plugin-poc/sync_references.py
claude plugin validate ./claude-plugin-poc --strict
claude --plugin-dir ./claude-plugin-poc

# in session
/gendd:create-context-pack
# edit skills/…/SKILL.md, then:
/reload-plugins

Adding a skill is a new skills/<name>/SKILL.md plus two or three ref lines. That is the whole authoring loop.

05 · PHASE 0 — THE WORKED EXAMPLE

Verify what already works, and build nothing — complete

The cheapest possible first move, and it answered the only question that mattered: are the copies in the plugin still identical to the corpus documents they came from? They are — all three, verified byte-for-byte. Had one differed, the finding would have been that the corpus had already moved on without the plugin.

WHAT CHANGES

Nothing. Not one file.

No script, no directory, no move. skills/enhance-requirements/SKILL.md stays where it is; the three files in references/ stay where they are. The plugin is already correct — it was assembled by hand with cmp-verified fidelity, and the mapping is already written down in prose in README.md and in SKILL.md's own reference table.

What phase 0 actually does is establish the fact that those copies still match their sources, so that every later phase has a known-good starting point to diff against.

THE PROOF

Three diffs, run by hand

If these are silent, the plugin is in sync with the corpus and the whole premise of the plan holds.

cd agent-assets
R=claude-plugin-poc/references/enhance-requirements

diff "$R/enhance-requirements.md" \
     gendd-analysis/playbooks/on-demand/enhance-requirements.md
diff "$R/enhance-acceptance-criteria.md" \
     gendd-analysis/workflows/enhance-acceptance-criteria.md
diff "$R/requirements-enhancement.md" \
     gendd-analysis/templates/requirements-enhancement.md

# and confirm the plugin itself is sound
claude plugin validate ./claude-plugin-poc --strict

If any of them is not silent, that is the finding: the corpus has already moved on without the plugin, and phase 1 starts by deciding which side is right.

THEN, AND ONLY THEN

Skill #2 is what pays for the script

Add create-context-pack: a new skills/create-context-pack/SKILL.md and three more corpus files copied into references/. That is the moment the by-hand approach starts to cost more than the script — six files to keep straight instead of three, across two capabilities whose sources sit in different corpus directories.

Write sync_references.py here, with both skills in it, and the earlier diffs become --check in CI.

NOT IN THIS PHASE

Nothing is published or retired

No marketplace edit, no managed-settings change, no version bump, no new file in git. /gendd:enhance-requirements behaves exactly as it does today for everyone who has it.

Phase 0 is done when the four commands above pass. It is a verification step, not a construction step — and that is the point: it establishes the baseline the rest of the plan diffs against.

07 · SEQUENCE AFTER PHASE 0

Highest return first, and the gaps last

PHASE 1
Package what's already written
Adds skills + the
sync script.
Publishes at the end.

The six steps whose method exists in full and can't be invoked: 02, 03, 05, 11, 18, 20. Wrappers only, no authoring — the highest return in the plan. Order: create-context-pack → incremental-doc-update → generate-ide-rules → the rest. Context in, context maintained, then everything else.

Run scripts/benchmark-plugin.sh once around eight skills and again at fourteen. Two data points tell you the real per-skill standing cost, which is the number that decides whether one plugin holds.

Publish when

The first three are producing output a Tech Lead accepts. Then bump the version — one commit and a push, since autoUpdate is already on.

PHASE 2
Fold in the .skill packages
Needs a decision
before any code.

Nine .skill packages plus the QA toolset come from a different lineage than the corpus, and six capabilities are covered by both. Decide the canonical lineage per capability first — otherwise you ship two answers to the same question in one namespace.

Rule of thumb: where a .skill ships working scripts (test-gap-analyzer, cicd-pipeline-audit, release-evidence-packet, architecture-diagram-generator), it wins. Where it's prose duplicating a workflow, the corpus wins.

Housekeeping that must land here: the duplicate requirements-enhancer packages, the stories-from-source / _v2 pair, the stray jira-story-estimator 1.skill filename, and the live .env in the TestRail MCP folder.

PHASE 4
The Desktop build
Second output
from the same map.

Product, design and QA people reach skills through the chat console at admin-settings/plugins, which does not reach Claude Code — two consoles, two packages. Same references, a second output target, and one field flipped: disable-model-invocation is right for an engineer typing a command and wrong for chat, where the description is what makes a skill trigger. Note

GitHub sync on that console requires a private or internal repo, and a .zip needs .claude-plugin/ at the archive root, not nested.

LATER
Split, only on a signal
Not on a schedule.

Two signals, both measurable rather than felt: the benchmarked standing cost of the skill descriptions becomes material, or you want to hold one area's release back while shipping another. Until one of those happens, one plugin is the simpler system.

Splitting later is cheap on the build side — change the map, rerun the script — and expensive on the human side, because the namespace changes. Use the marketplace entry's renames field to carry identity across when the day comes.

Also parked

guardrails/: hooks for deterministic enforcement, governance text compiled into references, and — outside any plugin — the permission deny-list in managed settings.

08 · DECIDE OR TEST BEFORE PHASE 1

Three items, one of them a fifteen-minute experiment

Test the clone behaviour yourself
Whether a relative-path source clones the whole repo or only the plugin directory is undocumented. If the whole repo lands on disk, ${CLAUDE_PLUGIN_ROOT}/../../ would remove the copying entirely and shrink this design a lot. Install the plugin from the marketplace and list the cache directory — that's the whole experiment. I'd still ship the build step either way, because undocumented behaviour can change under you, but it's worth knowing what you're buying.
Generated files in git need a convention
references/ becomes generated but stays committed, which is unusual enough to surprise a contributor. Say so where they'll see it: a line in README.md, a .gitattributes marking it linguist-generated so diffs collapse in review, and --check in CI as the actual enforcement.
Two "written" skills are thinner than they look
greenfield-analysis.md is 4 KB against brownfield's 18 KB, and the bundled enhance-requirements copies carry cross-links that were already dead upstream. Packaging exposes thin content rather than hiding it — budget for filling those in during phase 1 rather than discovering them in phase 3.
