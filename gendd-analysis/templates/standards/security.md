## Purpose

Establish security practices that protect the application, its data, and its users. These standards are non-negotiable baselines -- they apply to all code, whether written by humans or AI agents. Security is not a feature; it is a constraint on every feature.

## Audience

All developers, DevOps engineers, QA engineers, and AI coding agents contributing to this repository. Security-specific sections (incident response, compliance) also apply to engineering managers and security officers.

## Standards

### Authentication & Authorization

#### MUST (Non-Negotiable)

| # | Standard | Rationale | Verification |
|---|----------|-----------|-------------|
| 1 | Verify authentication on every request -- do not cache authentication decisions | Stale auth state leads to unauthorized access | Integration tests, security review |
| 2 | Use standard protocols (OAuth2, OIDC, JWT with proper validation) | Custom auth schemes have unknown vulnerabilities | Architecture review |
| 3 | Validate JWT signatures, expiration, issuer, and audience on every request | Prevents token forgery, replay, and misuse | Automated tests |
| 4 | Check authorization before every action -- fail closed (deny if check fails) | Fail-open is the most dangerous authorization bug | Integration tests |
| 5 | Log authentication failures (without logging credentials) | Enables detection of brute force and credential stuffing | Log monitoring |
| 6 | Enforce account lockout after {MAX_FAILED_ATTEMPTS} consecutive failed login attempts | Prevents brute force attacks | Automated tests |
| 7 | Use HTTPS for all authentication endpoints -- no exceptions | Credentials in transit must be encrypted | Infrastructure config |

#### SHOULD (Recommended)

| # | Standard | Rationale | When to Apply |
|---|----------|-----------|---------------|
| 1 | Implement rate limiting on authentication endpoints | Slows brute force and credential stuffing | All auth endpoints |
| 2 | Support multi-factor authentication (MFA) for privileged accounts | Defense in depth | Admin and elevated-privilege accounts |
| 3 | Use short-lived tokens with refresh token rotation | Limits exposure window if a token is compromised | All token-based auth |
| 4 | Implement session timeout and idle timeout | Prevents abandoned sessions from being hijacked | All user sessions |

#### MAY (Optional Best Practices)

| # | Standard | Benefit | Trade-off |
|---|----------|---------|-----------|
| 1 | Use passwordless authentication (passkeys, magic links) | Eliminates password-related vulnerabilities | User experience change |
| 2 | Implement step-up authentication for sensitive operations | Contextual security without friction for low-risk actions | Implementation complexity |

### Secrets Management

#### MUST (Non-Negotiable)

| # | Standard | Rationale | Verification |
|---|----------|-----------|-------------|
| 1 | Never hardcode secrets, credentials, API keys, tokens, certificates, or private keys in source code | Secrets in code are exposed in version history permanently | Secret scanning (CI), PR review |
| 2 | Store secrets in a dedicated secret management system (Vault, AWS Secrets Manager, Azure Key Vault, etc.) or environment variables | Centralized, auditable, rotatable | Infrastructure review |
| 3 | Secret files (`.env`, credentials files) are listed in `.gitignore` | Prevents accidental commits | `.gitignore` check |
| 4 | Rotate secrets on a defined cadence and immediately after any suspected compromise | Limits exposure window | Operations runbook |
| 5 | Use separate secrets per environment (dev, staging, production) | Compromise of one environment does not affect others | Infrastructure review |

#### SHOULD (Recommended)

| # | Standard | Rationale | When to Apply |
|---|----------|-----------|---------------|
| 1 | Run automated secret scanning in CI (e.g., git-secrets, truffleHog, GitHub secret scanning) | Catches secrets before they reach the repository | All repositories |
| 2 | Use service accounts with least-privilege permissions for automated processes | Limits blast radius | CI/CD pipelines, background jobs |
| 3 | Audit secret access logs regularly | Detects unauthorized access | Production environments |

**Secret Categories:**

| Category | Examples |
|----------|----------|
| Authentication | Passwords, API keys, tokens, certificates, private keys |
| Connection Strings | Database credentials, service URLs with embedded passwords |
| Encryption | Encryption keys, signing keys, salt values |
| External Services | Third-party API keys, webhook secrets |

### Input Validation

#### MUST (Non-Negotiable)

| # | Standard | Rationale | Verification |
|---|----------|-----------|-------------|
| 1 | Validate all external input (user input, API payloads, file uploads, URLs, environment variables) | External input is the primary attack vector | Automated tests, PR review |
| 2 | Validate type, format, length, range, and encoding | Defense in depth against injection and overflow | Automated tests |
| 3 | Use parameterized queries for all database operations -- never string concatenation | Prevents SQL injection | Linter rules, automated tests |
| 4 | Encode user input before rendering in HTML, JavaScript, or other output contexts | Prevents XSS attacks | Automated tests, PR review |
| 5 | Validate file uploads (type, size, content) -- never trust file extensions alone | Prevents malicious file uploads | Automated tests |

#### SHOULD (Recommended)

| # | Standard | Rationale | When to Apply |
|---|----------|-----------|---------------|
| 1 | Use allowlists over denylists for input validation | Allowlists are more secure -- denylists can be bypassed | All input validation |
| 2 | Validate on both client and server -- server validation is the authority | Client validation is a UX convenience, not a security control | All forms and APIs |
| 3 | Sanitize and normalize input before processing (trim whitespace, normalize unicode) | Prevents bypass via encoding tricks | All text input |

### Data Protection

#### MUST (Non-Negotiable)

| # | Standard | Rationale | Verification |
|---|----------|-----------|-------------|
| 1 | Encrypt data in transit using TLS 1.2 or higher | Prevents eavesdropping and man-in-the-middle attacks | Infrastructure config, SSL scan |
| 2 | Encrypt sensitive data at rest (PII, payment data, health records, credentials) | Compliance and breach mitigation | Infrastructure review |
| 3 | Use strong, current encryption algorithms (AES-256, RSA-2048+, SHA-256+) | Weak algorithms are breakable | Security review |
| 4 | Never store passwords in plaintext -- use bcrypt, scrypt, or argon2 with appropriate cost factors | Rainbow table and brute force resistance | Automated tests |
| 5 | Implement data retention policies -- delete data when no longer needed | Minimizes exposure surface | Compliance review |

#### SHOULD (Recommended)

| # | Standard | Rationale | When to Apply |
|---|----------|-----------|---------------|
| 1 | Use field-level encryption for highly sensitive data (SSN, card numbers) in addition to volume encryption | Defense in depth | When storing regulated data |
| 2 | Implement data masking for non-production environments | Prevents exposure of real data in dev/staging | All non-production environments |
| 3 | Log data access for sensitive records (audit trail) | Compliance and breach investigation | Regulated data |

### Logging (Security Perspective)

#### MUST (Non-Negotiable)

| # | Standard | Rationale | Verification |
|---|----------|-----------|-------------|
| 1 | Never log sensitive data | Compliance (PCI, HIPAA, GDPR) and security | PR review, automated scanning |
| 2 | Log security-relevant events (authentication failures, authorization denials, input validation failures, privilege changes) | Enables detection and forensics | Log monitoring |
| 3 | Include correlation IDs, timestamps, source IP, and user context in security logs | Enables tracing and investigation | Log format review |
| 4 | Protect log storage -- logs are append-only, access-controlled, and tamper-evident | Prevents attackers from covering their tracks | Infrastructure review |

**What to Log:**

| Event | Details to Include |
|-------|-------------------|
| Login success/failure | User ID, IP, timestamp, method |
| Authorization denial | User ID, resource, action attempted |
| Input validation failure | Endpoint, field, validation rule (not the input value if sensitive) |
| Privilege changes | Who, what changed, by whom, timestamp |
| Secret access | Which secret, by which service/user, timestamp |

**What NEVER to Log:**

| Category | Examples |
|----------|----------|
| Authentication Credentials | Passwords, API keys, tokens, session IDs, JWTs |
| Payment Card Data | Full card numbers, CVV, PINs |
| Personal Identifiers | SSN, driver's license, passport numbers |
| Health Information | Medical records, diagnoses |
| Private Keys/Secrets | Encryption keys, certificates |

**Masking Guidelines:**

| Data Type | Masking Rule |
|-----------|-------------|
| Credit card | Last 4 only (`****4242`) |
| Email | Partial (`j***@example.com`) |
| Token | Never log -- use request ID instead |
| Phone | Last 4 only (`***-***-1234`) |

### Multi-Tenant Isolation

#### MUST (Non-Negotiable)

| # | Standard | Rationale | Verification |
|---|----------|-----------|-------------|
| 1 | Every backend database operation includes tenant context | Prevents cross-tenant data leakage | Integration tests |
| 2 | Tenant context is derived server-side from the authenticated session -- never from client-supplied IDs | Client-supplied tenant IDs can be tampered with | Security review |
| 3 | Cross-tenant data access is architecturally impossible -- enforced at the data access layer | Defense in depth | Architecture review, integration tests |
| 4 | Test multi-tenant isolation explicitly (Tenant A cannot see Tenant B's data) | Validates the most critical data boundary | Automated tests |

**Tenant Models:**

| Tenant Model | How It Works |
|-------------|-------------|
| Database-per-tenant | Each tenant gets its own database; tenant resolved from request context |
| Schema-per-tenant | Shared database, separate schemas per tenant |
| Shared DB with tenant column | Single database, every table has a `tenant_id` column |
| Host-based routing | Tenant derived from request hostname or subdomain |

### Dependency Security

#### MUST (Non-Negotiable)

| # | Standard | Rationale | Verification |
|---|----------|-----------|-------------|
| 1 | Never add dependencies with known critical or high vulnerabilities | Supply chain attacks are a leading attack vector | Dependency scanning in CI |
| 2 | Run dependency vulnerability scanning on every PR | Catches new vulnerabilities before merge | CI pipeline |
| 3 | Pin dependency versions and commit lock files | Reproducible builds, prevents supply chain attacks | CI check |
| 4 | Remediate critical vulnerabilities within 24 hours, high within 7 days | Time-bound response prevents exposure | Vulnerability tracking |

#### SHOULD (Recommended)

| # | Standard | Rationale | When to Apply |
|---|----------|-----------|---------------|
| 1 | Use automated dependency update tools (Dependabot, Renovate) | Stay current with minimal manual effort | All repositories |
| 2 | Evaluate new dependencies for maintenance status, license, and security history | Prevents adding abandoned or risky deps | When adding new deps |
| 3 | Run dependency audits on a regular cadence (weekly minimum) | Catches newly disclosed vulnerabilities | All repositories |
| 4 | Verify package integrity (checksums, signatures) | Prevents tampered packages | When available |

**Security Incident Severity:**

| Severity | Description | Response Time | Examples |
|----------|-------------|---------------|---------|
| P1 - Critical | Active breach, data exfiltration, system compromise | Immediate (15 min) | Unauthorized data access, ransomware, credential leak |

### Security Code Review Checklist

Use this checklist during code reviews for any PR that touches security-relevant code.

#### Secrets
- [ ] No hardcoded secrets, keys, or passwords
- [ ] Secret files are in `.gitignore`
- [ ] Secrets are loaded from secure sources (environment, vault)

#### Input Handling
- [ ] All external input is validated (type, format, length, range)
- [ ] SQL queries use parameterization
- [ ] User input is encoded before rendering
- [ ] File uploads are validated (type, size, content)

#### Authentication & Authorization
- [ ] Authentication is required for protected resources
- [ ] Authorization checks are in place before every action
- [ ] Principle of least privilege is followed
- [ ] Tokens are validated (signature, expiration, issuer, audience)

#### Logging
- [ ] No sensitive data in logs
- [ ] Security events are logged (auth failures, authz denials)
- [ ] Errors do not leak internal details to end users

#### Multi-Tenant Isolation
- [ ] Every database query includes tenant context
- [ ] Tenant context is derived server-side
- [ ] No code path allows cross-tenant data access

#### Data Protection
- [ ] Sensitive data is encrypted at rest and in transit
- [ ] Passwords are hashed with appropriate algorithms
- [ ] PII is handled according to compliance requirements

#### Dependencies
- [ ] No known critical/high vulnerabilities in dependencies
- [ ] Dependencies are from trusted sources
- [ ] Lock files are committed
