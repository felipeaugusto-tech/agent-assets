# Google Antigravity Rule Template

> Generated by GenDD-Flow
> This template produces `GEMINI.md`, `AGENTS.md`, and `.agent/rules/*.md` files for the target repository.

## About Google Antigravity

Google Antigravity (Gemini in IDE) uses a layered rule system with multiple file types. Rules have a defined priority order, and the system supports both IDE-specific and cross-tool formats.

### Priority Order (Highest to Lowest)

1. **`GEMINI.md`** -- IDE-specific, highest priority. Rules here override everything else.
2. **`AGENTS.md`** -- Cross-tool standard. Also recognized by Cursor and Claude Code.
3. **`.agent/rules/*.md`** -- Granular rules for specific areas or file patterns.
4. **`.agent/workflows/*.md`** -- On-demand workflows (optional).
5. **`.agent/skills/*.md`** -- Reusable skills (optional).

### Global Rules (User-Level)

Users can also set global rules that apply across all projects:
- `~/.gemini/GEMINI.md` -- User-level IDE-specific rules
- `~/.gemini/AGENTS.md` -- User-level cross-tool rules

Project-level rules take priority over global rules.

## GenDD-Flow output format (required)

Use one `<!-- FILE: path -->` **per output file** (the CLI maps paths to the Antigravity layout). Allowed **marker** values:

| Marker | On disk |
|--------|---------|
| `GEMINI.md` | `GEMINI.md` (project root) |
| `AGENTS.md` | `AGENTS.md` (project root) |
| `rules/{name}.md` | `.agent/rules/{name}.md` |
| `workflows/{name}.md` | `.agent/workflows/{name}.md` |
| `skills/{name}.md` | `.agent/skills/{name}.md` |

Use a safe single-segment name for `{name}` (letters, numbers, dot, dash, underscore). No `../` or extra directories.

```markdown
<!-- FILE: GEMINI.md -->
# Gemini-specific rules
...

<!-- FILE: rules/security.md -->
# Security
...
```

### Directory Scoping

`AGENTS.md` can be placed in subdirectories to scope rules to specific parts of a monorepo. A `packages/api/AGENTS.md` applies when working within that directory.

## Generated Files

### 1. GEMINI.md (Project Root -- Highest Priority)

IDE-specific rules for Gemini. Use this for Gemini-specific behavior and overrides.

```markdown
# {PROJECT_NAME} -- Gemini Rules

> These rules have the highest priority in Gemini and override AGENTS.md and .agent/rules/.

## Gemini-Specific Behavior

- When generating code, always check existing patterns in the codebase before proposing new ones.
- Prefer inline explanations over lengthy comments.
- When uncertain about a pattern, reference the context areas in `.agent/rules/` before asking.

## Project Identity

- **Name:** {PROJECT_NAME}
- **Type:** {BRIEF_DESCRIPTION}
- **Language:** {LANGUAGE}
- **Framework:** {FRAMEWORK}

## Critical Rules (Always Apply)

### Security
- Never hardcode secrets, credentials, API keys, or tokens
- Never log sensitive data (passwords, tokens, PII, card numbers)
- Validate all external input
- Use parameterized queries for all database operations
- Verify auth on every request

### Multi-Tenant
- Every database query includes tenant context (server-derived)
- Cross-tenant data access is architecturally impossible
- Tenant model: {TENANT_MODEL}

### Compliance
- Scope: {COMPLIANCE_SCOPE}

## Before Generating Code

1. Check if similar code exists
2. Follow existing patterns
3. Include error handling with context
4. Consider multi-tenant isolation
5. Add appropriate tests
```

Cross-tool standard that also works in Cursor and Claude Code. Use this for rules that should apply regardless of IDE.

```markdown

> Cross-tool agent instructions. Works in Gemini, Cursor, and Claude Code.

- **Language:** {LANGUAGE}
- **Framework:** {FRAMEWORK}

- Structure: Arrange-Act-Assert

```

### 3. .agent/rules/*.md (Granular Rules)

Individual rule files for specific SDLC areas. Each file provides detailed guidance for one area.

**File naming convention:** `{area-name}.md` (lowercase, hyphenated)

#### Example: .agent/rules/security.md

```markdown
# Security Rules

## Non-Negotiable

- Never hardcode secrets (passwords, API keys, tokens, certificates, private keys)
- Never log sensitive data (auth credentials, payment data, PII, health info)
- Validate all external input (type, format, length, range, encoding)
- Use parameterized queries -- never string concatenation in SQL
- Enforce multi-tenant isolation on every database operation
- Verify authentication and authorization on every request
- Return safe error messages to end users

## Secrets Management
{PROJECT_SPECIFIC_SECRETS_GUIDANCE}

## Input Validation Patterns
{PROJECT_SPECIFIC_VALIDATION_PATTERNS}

## Security Review Checklist
- No hardcoded secrets
- All input validated
- Parameterized queries
- No sensitive data in logs
- Auth checks present
- Tenant isolation enforced
```

#### Example: .agent/rules/testing.md

```markdown
# Testing Rules

## Structure
Every test: Arrange-Act-Assert

## Naming
Pattern: {TEST_NAMING_PATTERN}

## Required Scenarios
- Happy path, invalid input, not found (always)
- Auth, multi-tenant isolation (when applicable)

## Mocking
- Mock: External APIs, databases (unit tests), file system, time
- Do NOT mock: Code under test, value objects, pure functions

## E2E
- Selectors: `data-testid` only
- Waits: Explicit (`waitForSelector`) -- never `sleep()`
```

### 4. .agent/workflows/*.md (Optional On-Demand Workflows)

Workflows that can be invoked on demand, similar to Claude Code slash commands.

#### Example: .agent/workflows/review-code.md

```markdown
# Code Review Workflow

Review the specified code for:

1. Security issues (secrets, input validation, SQL injection, auth, tenant isolation)
2. Code quality (naming, error handling, single responsibility)
3. Test coverage (AAA, naming, scenarios)
4. Pattern consistency with the existing codebase

Output: Structured findings by severity (MUST FIX, SHOULD FIX, CONSIDER).
```

### 5. .agent/skills/*.md (Optional Reusable Skills)

Skills are reusable capabilities the agent can reference.

#### Example: .agent/skills/generate-tests.md

```markdown
# Test Generation Skill

When generating tests:
- Use {TEST_FRAMEWORK}
- Follow {TEST_NAMING_PATTERN}
- Apply Arrange-Act-Assert
- Cover: happy path, invalid input, not found, edge cases
- Add auth and multi-tenant scenarios when applicable
- Mock at boundaries only
```

## Usage Notes

- **GEMINI.md vs AGENTS.md:** Put Gemini-specific behavior (output format preferences, Gemini-specific capabilities) in `GEMINI.md`. Put universal rules in `AGENTS.md`.
- **Cross-tool compatibility:** `AGENTS.md` is recognized by multiple tools. Invest in this file for maximum portability.
- **Subdirectory scoping:** Use `AGENTS.md` in subdirectories for monorepo setups.
- **Keep files focused:** One area per file in `.agent/rules/`. Avoid large monolithic files.
- **Priority awareness:** If `GEMINI.md` and `AGENTS.md` conflict, `GEMINI.md` wins in Gemini.
