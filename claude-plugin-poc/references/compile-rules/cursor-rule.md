# Cursor Rule Template

> Generated by GenDD-Flow
> This template produces `.cursor/rules/*.mdc` files for the target repository.

## About Cursor Rules

Cursor uses MDC (Markdown Configuration) files stored in `.cursor/rules/` to instruct its AI assistant. Each rule file has YAML frontmatter that controls when the rule is active, followed by markdown content that the AI reads as instructions.

## Template

```markdown
---
description: {RULE_DESCRIPTION}
globs: {FILE_PATTERNS or leave empty for always-on}
alwaysApply: {true/false}
---

# {RULE_TITLE}

{Rule content derived from context areas and standards.
This content tells Cursor's AI how to behave when working with files matching the glob pattern.}

## Key Constraints
{Non-negotiable rules for this area}

## Patterns to Follow
{Coding patterns, naming conventions, architectural decisions}

## What NOT to Do
{Anti-patterns, common mistakes to avoid}
```

## Frontmatter Reference

| Field | Type | Description |
|-------|------|-------------|
| `description` | string | Short description of when/why this rule applies. Cursor uses this to decide relevance. |
| `globs` | string or array | File patterns that activate this rule (e.g., `"**/*.ts"`, `["src/**/*.py", "tests/**/*.py"]`). Leave empty for always-on rules. |
| `alwaysApply` | boolean | If `true`, the rule is always active regardless of context. If `false`, Cursor decides based on relevance. |

## File Organization

**Output format (required for GenDD-Flow):** Emit **one** HTML comment before each file’s content. The CLI splits your response into separate `.mdc` files. Use a **plain basename** only (e.g. `general.mdc`), not a path. Example:

```markdown
<!-- FILE: general.mdc -->
---
description: Core project rules
alwaysApply: true
---

# General
...

<!-- FILE: coding-standards.mdc -->
---
description: ...
alwaysApply: true
---

# Coding standards
...
```

Do not use `../`, subdirectories, or non-`.mdc` names in the `FILE:` line.

Generate the following files in `.cursor/rules/` (each as its own `<!-- FILE: ... -->` block as above):

| File | alwaysApply | globs | Purpose |
|------|-------------|-------|---------|
| `general.mdc` | true | (none) | Project identity, tech stack, security rules, key constraints |
| `coding-standards.mdc` | true | (none) | Naming conventions, error handling, formatting, logging |
| `testing.mdc` | false | `{TEST_FILE_PATTERNS}` | Test naming, AAA pattern, mocking guidelines, required scenarios |
| `{AREA_NAME}.mdc` | false | `{AREA_SPECIFIC_GLOBS}` | Area-specific rules derived from context area analysis |

## Example: general.mdc

```markdown
---
description: Core project rules that apply to all code generation and editing
alwaysApply: true
---

# {PROJECT_NAME} - General Rules

You are working on {PROJECT_NAME}, a {BRIEF_DESCRIPTION}.

## Tech Stack
- Language: {LANGUAGE}
- Framework: {FRAMEWORK}
- Database: {DATABASE}
- Infrastructure: {INFRASTRUCTURE}

## Key Constraints
- Multi-tenant: Always include tenant context in database queries (server-derived, never client-supplied)
- Security: Never hardcode secrets, never log sensitive data, validate all input, use parameterized queries
- Compliance: {COMPLIANCE_SCOPE}

## Before You Generate Code
1. Check if similar code already exists in the codebase
2. Follow existing patterns in the relevant module
3. Include error handling with context
4. Consider multi-tenant isolation
5. Add appropriate tests
```

## Example: testing.mdc

```markdown
---
description: Testing standards for test files
globs: "{TEST_FILE_PATTERNS}"
alwaysApply: false
---

# Testing Standards

## Test Structure
Every test follows the Arrange-Act-Assert pattern:
- ARRANGE: Set up test data and mocks
- ACT: Call the code under test
- ASSERT: Verify the result

## Naming
Use the pattern: {TEST_NAMING_PATTERN}

## Required Scenarios
- Happy path (valid input, expected output)
- Invalid input (null, empty, out of range)
- Not found (unknown ID or missing resource)
- Authorization (when code checks permissions)
- Multi-tenant isolation (when applicable)

## Mocking
- Mock external boundaries (APIs, databases in unit tests, file system, time)
- Never mock the code under test, value objects, or pure functions

## What NOT to Do
- Do not use `sleep()` or `waitForTimeout()` in E2E tests
- Do not share mutable state between tests
- Do not use CSS classes or XPath for E2E selectors -- use `data-testid`
```

## Usage Notes

- Content for each rule file is derived from the project's context areas and standards.
- Keep individual rule files focused -- one area per file.
- Cursor has a context window limit; avoid duplicating content across rules.
- The `description` field is critical -- Cursor uses it to decide when to apply non-always-on rules.
