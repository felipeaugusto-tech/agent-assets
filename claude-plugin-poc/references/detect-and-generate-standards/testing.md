### Test Pyramid

#### MUST (Non-Negotiable)

| # | Standard | Rationale | Verification |
|---|----------|-----------|-------------|
| 1 | Maintain a healthy test pyramid: many unit tests, fewer integration tests, fewest E2E tests | Fast feedback, maintainable suite, cost-effective | Test count ratios in CI metrics |

### Test Structure (Arrange-Act-Assert)

#### MUST (Non-Negotiable)

| # | Standard | Rationale | Verification |
|---|----------|-----------|-------------|
| 1 | Every test follows the AAA pattern: Arrange (setup), Act (execute), Assert (verify) | Consistent structure makes tests readable and maintainable | PR review |
| 2 | Each test verifies one logical behavior | Multiple assertions testing different behaviors mask failures | PR review |
| 3 | Assert section clearly states what is being verified | Failing tests should immediately communicate what broke | PR review |

#### SHOULD (Recommended)

| # | Standard | Rationale | When to Apply |
|---|----------|-----------|---------------|
| 1 | Separate the three sections with blank lines or comments | Visual clarity | All tests |
| 2 | Keep the Arrange section minimal -- use builders or factories for complex setup | Reduces noise, focuses on the behavior being tested | Tests with complex setup |

```
ARRANGE - Set up the test scenario (create test data, configure mocks)
ACT     - Execute the code being tested (call the method/function)
ASSERT  - Verify the results (check return values, verify side effects)
```

### Test Independence

#### MUST (Non-Negotiable)

| # | Standard | Rationale | Verification |
|---|----------|-----------|-------------|
| 1 | No shared mutable state between tests | Shared state causes order-dependent failures | CI (randomized test order) |
| 2 | Tests can run in any order and produce the same result | Order dependency is a common source of flakiness | CI configuration |
| 3 | Each test creates its own data and cleans up after itself | Prevents test pollution | PR review |
| 4 | Database changes are rolled back or isolated per test | Prevents data leakage between tests | Test lifecycle hooks |

#### SHOULD (Recommended)

| # | Standard | Rationale | When to Apply |
|---|----------|-----------|---------------|
| 1 | Use fresh instances of dependencies (mocks, fakes) per test | Prevents mock state leakage | Unit tests with mocks |
| 2 | Use transactions for database isolation in integration tests | Fast rollback, no cleanup needed | DB-backed integration tests |

### Mocking Guidelines

#### MUST (Non-Negotiable)

| # | Standard | Rationale | Verification |
|---|----------|-----------|-------------|
| 1 | Mock at boundaries (external APIs, databases in unit tests, file system, time, network) | Isolates the code under test from unreliable externals | PR review |
| 2 | Never mock the code under test | Defeats the purpose of the test | PR review |
| 3 | Never mock simple value objects, DTOs, or pure functions | No benefit, adds complexity | PR review |

#### SHOULD (Recommended)

| # | Standard | Rationale | When to Apply |
|---|----------|-----------|---------------|
| 1 | Prefer fakes over mocks for complex collaborators | Fakes test behavior, mocks test implementation | When the collaborator has complex behavior |
| 2 | Verify mock interactions only when the interaction is the behavior being tested | Over-verification makes tests brittle | All mock-based tests |
| 3 | Use mock/stub/spy terminology consistently within the project | Reduces confusion | Team agreement |

**What to Mock:**

| Category | Examples | Why Mock |
|----------|----------|----------|
| External APIs | Payment gateways, third-party services | Unreliable, slow, cost money |
| Databases (unit tests) | Repository calls | Isolate business logic |
| File System | File reads/writes | Avoid test pollution |
| Time/Randomness | Current time, random values | Reproducible tests |
| Network | HTTP clients, message queues | Avoid flaky tests |

**What NOT to Mock:**

| Category | Examples | Why Not Mock |
|----------|----------|--------------|
| Code under test | The class/function being tested | Defeats the purpose |
| Simple value objects | DTOs, data classes | No benefit, adds complexity |
| Pure functions | Math, string manipulation | Deterministic, fast |
| Internal implementation | Private methods | Test behavior, not implementation |

### CI/CD Integration

#### MUST (Non-Negotiable)

| # | Standard | Rationale | Verification |
|---|----------|-----------|-------------|
| 1 | Unit tests run on every PR and block merge on failure | First line of defense, fast feedback | CI pipeline config |
| 2 | Integration tests run on merge to main and block deployment on failure | Validates component integration before deploy | CI pipeline config |
| 3 | E2E / smoke tests run pre-production and block production deploy on failure | Final gate before users are affected | CI pipeline config |
| 4 | Tests must be deterministic -- no flaky tests in the suite | Flaky tests erode trust in the test suite | Flaky test tracking |

#### SHOULD (Recommended)

| # | Standard | Rationale | When to Apply |
|---|----------|-----------|---------------|
| 1 | Run smoke tests post-deploy and alert/rollback on failure | Catches deployment-specific issues | All production deploys |
| 2 | Unit tests complete in under 5 minutes, integration under 15 | Fast feedback keeps developers productive | CI optimization |
| 3 | Quarantine flaky tests rather than deleting them | Preserves coverage intent while restoring trust | When flakiness is detected |

**CI/CD Test Matrix:**

| Stage | Tests Run | Failure Action |
|-------|-----------|----------------|
| PR Created | Unit tests, linting | Block merge |
| PR Approved / Merge | Unit + Integration | Block deploy |
| Pre-production | E2E + Smoke | Block production deploy |
| Post-deploy | Smoke tests | Alert / rollback |
| Nightly | Full regression + E2E + Load | Alert (non-blocking) |

### E2E Testing Rules

#### MUST (Non-Negotiable)

| # | Standard | Rationale | Verification |
|---|----------|-----------|-------------|
| 1 | Use `data-testid` attributes for element selection -- never CSS classes, XPath, or text content | CSS classes and text change frequently; test IDs are stable | Linter rule, PR review |
| 2 | Use explicit waits (`waitForSelector`, `waitForResponse`) -- never `sleep()` or `waitForTimeout()` | Arbitrary delays are flaky and slow | Linter rule, PR review |
| 3 | Each E2E test starts from a clean, known state | Prevents order-dependent failures | Test setup hooks |
| 4 | E2E tests cover critical user journeys, not exhaustive permutations | E2E tests are expensive to maintain | Test plan review |

#### SHOULD (Recommended)

| # | Standard | Rationale | When to Apply |
|---|----------|-----------|---------------|
| 1 | Run E2E tests against a dedicated test environment, not shared staging | Prevents interference from other activities | When infrastructure allows |
| 2 | Use API calls for test setup (create users, seed data) rather than UI automation | Faster and more reliable setup | When APIs are available |
| 3 | Record screenshots/videos on failure for debugging | Speeds up failure diagnosis | CI configuration |

**Selector Rules:**

| Do | Don't |
|----|-------|
| `[data-testid="submit-button"]` | `button:has-text("Submit")` |
| `[data-testid="email-input"]` | `.btn-primary`, `#submit` |
| Explicit data attributes | XPath, text selectors, CSS classes |

**Waiting Rules:**

| Do | Don't |
|----|-------|
| `waitForSelector('[data-testid="..."]')` | `waitForTimeout(3000)` |
| `waitForResponse(...)` | `sleep(5000)` |
| `expect(...).toBeVisible()` | Arbitrary delays |

### Required Test Scenarios

#### Core Scenarios (Always Required)

| Scenario | Description |
|----------|-------------|
| Happy Path | Normal successful operation -- valid input returns expected output |
| Invalid Input | Null, empty, out-of-range values return validation errors |
| Not Found | Unknown ID or missing resource returns appropriate error |

#### Conditional Scenarios (When the Code Does This)

| Scenario | Applies When |
|----------|--------------|
| Authorization | Code checks permissions -- user without role gets denied |
| Authentication | Code requires auth -- missing token returns 401 |
| External Failure | Code calls external service -- timeout handled gracefully |
| Concurrency | Code handles parallel requests -- no data loss |
| Boundary Conditions | Numeric or size limits -- max, min, exactly at limit |
| Multi-Tenant Isolation | Multi-tenant context -- Tenant A cannot see Tenant B's data |

#### Domain-Specific Scenarios (Only When Applicable)

| Domain | Key Scenarios |
|--------|---------------|
| Payment / Financial | Card validation, declined transactions, retry/idempotency, sensitive field masking |
| Email / Notifications | Correct triggers, template data population, deduplication |
| Security / Auth | Account lockout, password policy, session/token expiry |
| Frontend / UI | Responsive breakpoints, accessibility (WCAG 2.1 AA), keyboard navigation |
| Regression / Sanity | Health endpoint smoke test, critical-path regression suite |

### Test Code Review Checklist

- [ ] Tests follow AAA pattern
- [ ] Test names communicate intent
- [ ] Tests are independent (no shared state, no order dependency)
- [ ] Happy path, error cases, and edge cases covered
- [ ] Tests are not flaky
- [ ] Mocks used at boundaries, not over-mocked
- [ ] Test data is clear (builders/fixtures for complex data)
- [ ] No production data or real secrets in tests
- [ ] E2E tests use `data-testid` selectors and explicit waits
- [ ] New code does not decrease coverage
