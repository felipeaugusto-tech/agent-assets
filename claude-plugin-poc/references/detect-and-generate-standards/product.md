## Purpose

Define consistent practices for product management activities -- from writing user stories to managing the backlog. These standards ensure that requirements are clear, testable, and traceable, reducing rework and miscommunication between product, engineering, and QA.

## Audience

Product managers, product owners, business analysts, QA engineers, and developers who write or refine requirements.

## Standards

### Story Writing

#### MUST (Non-Negotiable)

| # | Standard | Rationale | Verification |
|---|----------|-----------|-------------|
| 1 | Every user story follows the format: "As a {persona}, I want {action}, so that {outcome}" | Ensures every story has a clear user, action, and value | Backlog grooming review |
| 2 | Every story has at least one acceptance criterion in Given-When-Then format | Testable criteria reduce ambiguity | Definition of Ready check |
| 3 | Stories are small enough to complete within a single sprint | Large stories hide complexity and risk | Sprint planning review |
| 4 | Stories reference the user persona from the project's persona list | Keeps the user perspective grounded | Backlog grooming review |

#### SHOULD (Recommended)

| # | Standard | Rationale | When to Apply |
|---|----------|-----------|---------------|
| 1 | Include edge cases and error scenarios in acceptance criteria | Prevents late-stage discovery of missing behavior | All stories with user input or external dependencies |
| 2 | Attach wireframes or mockups for UI-related stories | Reduces interpretation gaps | UI/UX stories |
| 3 | Include technical notes for stories with non-obvious implementation constraints | Helps developers estimate accurately | Complex or integration-heavy stories |

#### MAY (Optional Best Practices)

| # | Standard | Benefit | Trade-off |
|---|----------|---------|-----------|
| 1 | Use story mapping to visualize user journeys before writing individual stories | Better coverage of end-to-end flows | Time investment upfront |

**Story Template:**

```
Title: {Concise description of the feature/change}

As a {persona},
I want {action/feature},
so that {business value/outcome}.

### Acceptance Criteria

**Scenario 1: {Happy path description}**
Given {precondition}
When {action}
Then {expected result}

**Scenario 2: {Edge case or error description}**
Given {precondition}
When {action}
Then {expected result}

### Notes
- {Technical notes, constraints, dependencies}
- {Link to design/wireframe if applicable}
```

### Definition of Ready

#### MUST (Non-Negotiable)

| # | Standard | Rationale | Verification |
|---|----------|-----------|-------------|
| 1 | Story has a clear title and description in the standard format | Team can understand what is being asked | Grooming checklist |
| 2 | Acceptance criteria are written in Given-When-Then format | Criteria are testable and unambiguous | Grooming checklist |
| 3 | Dependencies are identified and documented | Prevents blockers mid-sprint | Grooming checklist |
| 4 | Story is estimated by the development team | Team has assessed complexity | Sprint planning |
| 5 | UX designs are attached for UI stories | Developers know what to build | Grooming checklist |

#### SHOULD (Recommended)

| # | Standard | Rationale | When to Apply |
|---|----------|-----------|---------------|
| 1 | Story has been discussed in at least one grooming session | Shared understanding across the team | All stories before entering a sprint |
| 2 | Edge cases and negative scenarios are documented | Reduces surprises during development | Stories with user input, permissions, or integrations |
| 3 | Test data requirements are identified | QA can prepare test environments | Stories requiring specific data conditions |

### Definition of Done

#### MUST (Non-Negotiable)

| # | Standard | Rationale | Verification |
|---|----------|-----------|-------------|
| 1 | All acceptance criteria pass | Feature meets requirements | QA sign-off |
| 2 | Code is peer-reviewed and approved | Quality gate before merge | PR approval |
| 3 | All automated tests pass (unit, integration as applicable) | No regressions introduced | CI pipeline |
| 4 | Code is merged to the main branch | Feature is integrated | Git history |
| 5 | No critical or high-severity bugs remain open for the story | Feature is production-quality | Bug tracker |

#### SHOULD (Recommended)

| # | Standard | Rationale | When to Apply |
|---|----------|-----------|---------------|
| 1 | Documentation is updated if the feature changes existing behavior | Users and developers can understand the change | Features that alter APIs, workflows, or configurations |
| 2 | Feature is demonstrated to the product owner | Validates that the implementation matches intent | Sprint review |
| 3 | Performance impact has been assessed | Prevents production performance surprises | Features with data-intensive operations |

### Backlog Management

#### MUST (Non-Negotiable)

| # | Standard | Rationale | Verification |
|---|----------|-----------|-------------|
| 1 | Backlog is prioritized using a consistent method (MoSCoW, WSJF, RICE, or equivalent) | Ensures the team works on the highest-value items | Backlog review |
| 2 | Top of backlog (next 1-2 sprints) contains only stories that meet Definition of Ready | Prevents pulling unready work into sprints | Sprint planning gate |
| 3 | Stale items (untouched for 3+ months) are reviewed and either re-prioritized or archived | Prevents backlog bloat | Quarterly backlog cleanup |

#### SHOULD (Recommended)

| # | Standard | Rationale | When to Apply |
|---|----------|-----------|---------------|
| 1 | Hold backlog grooming sessions at least once per sprint | Keeps the backlog healthy and ready | Every sprint |
| 2 | Tag stories with epic, theme, or initiative labels | Enables tracking progress at higher levels | All stories |
| 3 | Limit backlog size to 3-6 months of estimated work | Prevents waste on items that may never be built | Ongoing |

#### MAY (Optional Best Practices)

| # | Standard | Benefit | Trade-off |
|---|----------|---------|-----------|
| 1 | Use a "Now / Next / Later" board view for strategic alignment | Clear communication of priorities to stakeholders | Requires regular curation |
| 2 | Track value delivered per sprint (velocity + business outcomes) | Connects engineering output to business impact | Requires instrumentation |

### Acceptance Criteria

#### MUST (Non-Negotiable)

| # | Standard | Rationale | Verification |
|---|----------|-----------|-------------|
| 1 | Use Gherkin format (Given-When-Then) for all acceptance criteria | Industry standard, directly translatable to automated tests | Grooming review |
| 2 | Each criterion tests one behavior | Prevents compound criteria that are hard to verify | Grooming review |
| 3 | Include at least one positive (happy path) and one negative (error/edge) scenario | Ensures both success and failure paths are defined | Grooming review |

#### SHOULD (Recommended)

| # | Standard | Rationale | When to Apply |
|---|----------|-----------|---------------|
| 1 | Include boundary conditions (min, max, empty, null) | Catches off-by-one and edge case bugs | Numeric inputs, lists, strings |
| 2 | Include security-relevant scenarios (unauthorized access, invalid tokens) | Prevents security gaps | Features with auth or permissions |
| 3 | Include multi-tenant scenarios where applicable | Ensures data isolation | Multi-tenant features |

**Gherkin Template:**

```gherkin
Feature: {Feature name}
  As a {persona}
  I want {action}
  So that {outcome}

  Scenario: {Happy path description}
    Given {precondition}
    And {additional precondition}
    When {action taken by user}
    Then {observable outcome}
    And {additional outcome}

  Scenario: {Error case description}
    Given {precondition}
    When {invalid action or condition}
    Then {error handling behavior}
    And {user feedback}

  Scenario Outline: {Parameterized test description}
    Given {precondition with <variable>}
    When {action with <input>}
    Then {outcome with <expected>}

    Examples:
      | variable | input | expected |
      | {val1}   | {in1} | {exp1}   |
      | {val2}   | {in2} | {exp2}   |
```

### Epic Structure

#### MUST (Non-Negotiable)

| # | Standard | Rationale | Verification |
|---|----------|-----------|-------------|
| 1 | Every epic has a clear business objective and measurable success criteria | Prevents epics from becoming open-ended | Epic kickoff review |
| 2 | Epics are broken down into stories before work begins | Enables estimation and incremental delivery | Grooming review |
| 3 | Epic has an owner (product manager or product owner) | Single point of accountability | Backlog metadata |

#### SHOULD (Recommended)

| # | Standard | Rationale | When to Apply |
|---|----------|-----------|---------------|
| 1 | Include a high-level architecture or approach document for technical epics | Aligns the team before implementation starts | Epics with significant technical scope |
| 2 | Define exit criteria at the epic level (what "done" looks like for the whole epic) | Prevents scope creep | All epics |
| 3 | Estimate epic duration in sprints, not just story points | Helps with roadmap planning | Roadmap-level planning |

- [ ] {Story 1}

- [ ] {Story 3}

- {External dependency or prerequisite}

- {Known risk and mitigation}
```

### Bug Reporting

#### MUST (Non-Negotiable)

| # | Standard | Rationale | Verification |
|---|----------|-----------|-------------|
| 1 | Every bug report includes: steps to reproduce, expected result, actual result | Enables developers to reproduce and diagnose | Bug triage review |
| 2 | Every bug has a severity classification (Critical, High, Medium, Low) | Enables prioritization | Bug triage |
| 3 | Environment information is included (browser, OS, API version, tenant) | Context-dependent bugs are common | Bug report template |

#### SHOULD (Recommended)

| # | Standard | Rationale | When to Apply |
|---|----------|-----------|---------------|
| 1 | Include screenshots or screen recordings | Visual evidence speeds up diagnosis | UI bugs |
| 2 | Include relevant log excerpts or error messages | Speeds up root cause analysis | Backend bugs |
| 3 | Note whether the bug is a regression (worked before, now broken) | Helps prioritize and narrow the search | When known |

**Bug Report Template:**

```
Title: {Short description of the bug}
Severity: {Critical / High / Medium / Low}
Environment: {Production / Staging / Dev} | {Browser/OS/Version}
Reported By: {Name}
Date: {Date}

### Steps to Reproduce
1. {Step 1}
2. {Step 2}
3. {Step 3}

### Expected Result
{What should happen}

### Actual Result
{What actually happens}

### Screenshots / Recordings
{Attach or link}

### Logs / Error Messages
{Relevant log output}

### Additional Context
- Regression: {Yes/No}
- Related Story/Epic: {Link}
- Affected Users/Tenants: {Scope}

### Requirements Traceability

#### MUST (Non-Negotiable)

| # | Standard | Rationale | Verification |
|---|----------|-----------|-------------|
| 1 | Every story links to its parent epic or initiative | Enables top-down progress tracking | Backlog metadata |
| 2 | Every PR references the story or ticket it implements | Enables code-to-requirement tracing | PR template enforcement |
| 3 | Test cases reference the acceptance criteria they verify | Enables requirement-to-test coverage analysis | Test management tool |

#### SHOULD (Recommended)

| # | Standard | Rationale | When to Apply |
|---|----------|-----------|---------------|
| 1 | Maintain a traceability matrix for compliance-critical features | Audit readiness | Regulated features (PCI, HIPAA, SOC2) |
| 2 | Tag stories with the compliance requirement they address | Enables compliance reporting | Regulated domains |

#### MAY (Optional Best Practices)

| # | Standard | Benefit | Trade-off |
|---|----------|---------|-----------|
| 1 | Use automated traceability tools that link commits to stories to test results | End-to-end visibility | Tooling cost and setup |
