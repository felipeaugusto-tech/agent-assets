### Naming Conventions

#### MUST (Non-Negotiable)

| # | Standard | Rationale | Verification |

### Error Handling

#### MUST (Non-Negotiable)

| # | Standard | Rationale | Verification |
|---|----------|-----------|-------------|
| 1 | Never silently swallow errors -- handle or propagate every error | Hidden failures cause cascading issues | Linter rules, PR review |
| 2 | Fail fast -- check preconditions at function entry | Reduces debugging time, prevents invalid state | PR review |
| 3 | Provide context in error messages (what failed, why, what to do) | Accelerates diagnosis in production | PR review |
| 4 | Clean up resources on error paths (close connections, release locks) | Prevents resource leaks | PR review |
| 5 | Never expose internal details (stack traces, DB schema, file paths) in API responses | Security risk -- information disclosure | Automated test, PR review |

#### SHOULD (Recommended)

| # | Standard | Rationale | When to Apply |
|---|----------|-----------|---------------|
| 1 | Use typed/custom error classes for domain errors | Enables precise error handling by callers | Business logic layers |
| 2 | Wrap third-party errors with domain context before propagating | Prevents leaking implementation details | Integration boundaries |
| 3 | Log errors with correlation/request IDs | Enables tracing across services | All services |

#### MAY (Optional Best Practices)

| # | Standard | Benefit | Trade-off |
|---|----------|---------|-----------|
| 1 | Use Result/Either types instead of exceptions for expected failures | Explicit error paths, no hidden control flow | Learning curve, verbosity |

### Dependency Management

#### MUST (Non-Negotiable)

| # | Standard | Rationale | Verification |
|---|----------|-----------|-------------|
| 1 | Pin dependency versions (lock files committed to source control) | Reproducible builds across environments | CI check for lock file |
| 2 | Never add dependencies with known critical/high vulnerabilities | Supply chain security | Dependency scanning in CI |

### API Design

#### MUST (Non-Negotiable)

| # | Standard | Rationale | Verification |
|---|----------|-----------|-------------|
| 1 | Use consistent response envelope format across all endpoints | Clients can parse responses uniformly | Contract test / schema validation |
| 2 | Return appropriate HTTP status codes (2xx success, 4xx client error, 5xx server error) | Follows REST semantics, enables proper client handling | Integration tests |
| 3 | Validate all input at the API boundary | First line of defense against malformed/malicious data | Automated tests |
| 4 | Version APIs when introducing breaking changes | Prevents breaking existing consumers | API review |
| 5 | Use parameterized queries -- never string concatenation for SQL or query building | Prevents SQL injection | Linter rules, PR review |

#### SHOULD (Recommended)

| # | Standard | Rationale | When to Apply |
|---|----------|-----------|---------------|
| 1 | Document APIs with OpenAPI/Swagger or equivalent | Enables auto-generation of clients and docs | Public and internal APIs |
| 2 | Use pagination for list endpoints | Prevents unbounded response sizes | Any endpoint returning collections |
| 3 | Include request/correlation IDs in responses | Simplifies debugging across services | All API responses |

#### MAY (Optional Best Practices)

| # | Standard | Benefit | Trade-off |
|---|----------|---------|-----------|
| 1 | Use HATEOAS for discoverability | Self-documenting APIs | Added complexity |

### Logging

#### MUST (Non-Negotiable)

| # | Standard | Rationale | Verification |
|---|----------|-----------|-------------|
| 1 | Use structured logging (JSON or key-value pairs) | Enables log aggregation and search | Linter, PR review |
| 2 | Include timestamp, level, message, service/component in every log entry | Minimum context for diagnosis | Logging framework config |
| 3 | Never log sensitive data (passwords, API keys, tokens, PII, card numbers, health info) | Compliance (PCI, HIPAA, GDPR) and security | PR review, automated scanning |
| 4 | Use appropriate log levels (ERROR for failures, WARN for handled anomalies, INFO for business events, DEBUG for diagnostics) | Enables filtering by severity in production | PR review |

#### SHOULD (Recommended)

| # | Standard | Rationale | When to Apply |
|---|----------|-----------|---------------|
| 1 | Include correlation/request IDs in log entries | Cross-service tracing | All request-scoped operations |
| 2 | Include tenant ID and user ID for multi-tenant systems | Scoped troubleshooting | Multi-tenant backends |
| 3 | Log duration for performance-sensitive operations | Performance monitoring | External calls, DB queries |
| 4 | Mask sensitive data when partial reference is needed (last 4 of card, partial email) | Balance between debugging and compliance | When referencing sensitive entities |

#### MAY (Optional Best Practices)

| # | Standard | Benefit | Trade-off |
|---|----------|---------|-----------|
| 1 | Use log sampling for high-volume endpoints | Reduces storage cost | May miss rare events |

| Production | On | On | On | Off | Off |

### Security (Non-Negotiable)

These rules apply universally across all code in the repository.

#### MUST (Non-Negotiable)

| # | Standard | Rationale | Verification |
|---|----------|-----------|-------------|
| 1 | Never hardcode secrets, credentials, API keys, tokens, or private keys in source code | Secrets in code are exposed in version history forever | Secret scanning (CI), PR review |
| 2 | Never log sensitive data (authentication credentials, payment card data, personal identifiers, health information, private keys) | Compliance violations (PCI, HIPAA, GDPR) and security breaches | Automated log scanning, PR review |
| 3 | Validate all external input (user input, API payloads, files, URLs, environment variables) for type, format, length, range, and encoding | Prevents injection, overflow, and malformed data attacks | Automated tests, PR review |
| 4 | Use parameterized queries for all database operations -- never string concatenation | Prevents SQL injection | Linter rules, automated tests |
| 5 | Enforce multi-tenant data isolation -- every backend query must include server-derived tenant context | Prevents cross-tenant data leakage | Integration tests, PR review |
| 6 | Verify authentication and authorization on every request -- do not cache auth decisions | Stale auth state leads to privilege escalation | Integration tests |
| 7 | Return safe error messages to end users -- never expose stack traces, DB schema, or internal paths | Information disclosure enables targeted attacks | Automated tests |

### Version Control (Commits, Branches, PRs)

#### MUST (Non-Negotiable)

| # | Standard | Rationale | Verification |
|---|----------|-----------|-------------|
| 1 | Write descriptive commit messages explaining what changed and why | Enables understanding changes without reading diffs | PR review |
| 2 | Keep PRs focused -- one logical change per PR | Easier to review, revert, and bisect | PR review |
| 3 | Self-review before requesting review | Catches obvious issues, respects reviewer time | PR checklist |
| 4 | Ensure CI passes before merging | Prevents broken builds on main | Branch protection rules |

#### SHOULD (Recommended)

| # | Standard | Rationale | When to Apply |
|---|----------|-----------|---------------|
| 1 | Use imperative mood in commit messages ("Add", "Fix", not "Added", "Fixed") | Convention adopted by most major projects | All commits |
| 2 | Reference ticket/issue numbers in commits and PRs | Traceability between code and requirements | When tickets exist |
| 3 | Keep PRs under 400 lines of changes | Large PRs get superficial reviews | All PRs |
| 4 | Differentiate must-fix from nice-to-have in code review comments | Prevents blocking PRs on style preferences | All reviews |

#### MAY (Optional Best Practices)

| # | Standard | Benefit | Trade-off |
|---|----------|---------|-----------|
| 1 | Use conventional commits format (`feat:`, `fix:`, `chore:`) | Enables automated changelogs | Requires team agreement |
| 2 | Squash commits on merge | Clean history | Loses granular commit history |
